# Landscape

A shared map of who is doing what in agent identity. Entries use the fields of the [approved field list](../approved-documents/2026-11-17-landscape-document-fields.md).

*The table is wide. Scroll sideways to see all fields.*

| Name | Type | Link | What it is | Where it touches agent identity | Does not cover | How it can be checked | Status, as of | Who added this |
|---|---|---|---|---|---|---|---|---|
| ARIA — Agent Registry for Identity & Authorization | Open specification, stewarded by a nonprofit | [aria.bar/spec](https://aria.bar/spec) | An accountability layer for AI agents crossing organizational boundaries. Credentials are W3C Verifiable Credentials, signed with a post-quantum composite signature. | Issues the credential an agent carries when it leaves its own trust domain, and defines the scope of what the agent is authorized to do. | What an agent does after admission. Runtime attestation. On-chain presentation. | Specification: public at aria.bar/spec. Credentials: anyone can verify an agent's signature, trust level, scopes and revocation status at aria.bar/verify without logging in; the check needs the ARIA resolver to be online, and the verifier currently reads a demonstration issuer. Code: open-source verification SDK and public resolver API. Working demo: thebunny.bar (issuer) and thecarrot.rest (receiver). | Implemented at L0 and L1 in the live environment. L2 and L3 in a testing environment. As of 2026-11-17. | Adolfo Grego Micha |
| agent.bar | Company platform (a credential issuer built on ARIA) | [agent.bar](https://agent.bar) | A web application where a person or an organization links their AI agents to an account and manages their credentials. The account holder opens a short enrollment window, each agent registers itself with its own keys (the private key never leaves the agent), and the holder can see and revoke credentials. A Tunolabs platform, separate from TrustLayer Foundation, which issues the credentials. Free to start. | Issues the ARIA credential that links each agent to the account that registered it, and so to the person or organization that answers for it. | How an agent behaves, or what it may access. A credential identifies the agent and does not grant access on its own; each receiver decides by its own policy. | Credentials it issues can be verified by anyone at aria.bar/verify (signature, trust level, scopes, revocation status) without logging in; the check needs the ARIA resolver to be online. The account holder sees the lifecycle of each credential in agent.bar; that record is not public. Today's issuer is a demonstration, and its credentials are not a production guarantee. | Live. L0 and L1 in the live environment, L2 and L3 in a testing environment. As of 2026-11-17. | Adolfo Grego Micha |
| AgentAvow | Company protocol | [agentavow.com](https://agentavow.com) | Checks the tools, MCP servers, packages and skills that AI agents connect to, and publishes a result for each: Safe to connect, Review before you connect, or Do not connect, over a 0 to 100 trust score, shown beside a separate adoption score. The result and trust score are signed with Ed25519 over RFC 8785 canonical bytes, and anyone can recompute them and verify the signature offline. | The tool side of an agent's connection, not the agent itself. A signed result is bound to a digest of the tool's exact definition, so a changed definition no longer matches. The signer is identified by did:web. | Issuing identities or credentials to agents, authorizing what an agent may do, or monitoring what a tool does after an agent connects. | Public verification key, open test vectors for the tool-definition digest with runs by three separately written checkers, and v0.1 conformance records posted to the Agent Conformance CG. | Implemented. As of 2026-10-16. | Kenne Ives |
| DEUSPROOF | Company protocol (a free, open registry) | [deusproof.com](https://deusproof.com) | A public, append-only register where an AI agent gets a birth certificate (a number, a date and a did:key identifier) and seals the SHA-256 fingerprints of what it produces: files, logs, mandates, agent cards. Each record is timestamped by an RFC 3161 authority and anchored to Bitcoin with OpenTimestamps. | Which agent, and since when. An agent can bind a key it generated itself by signing a fresh challenge, and from then on its records carry that signature. | Authorising what an agent may do, runtime attestation, or deciding who owns a work. | An open-source verifier (Apache-2.0) re-does the manifest signature, the ledger's Merkle inclusion, the RFC 3161 timestamp and the Bitcoin anchor on your own machine. From a saved bundle it runs without contacting the registry. | Implemented (public beta). As of 2026-10-26. | Michael Barbosa |
